# Xray 用户日志标识可读性修复

## 问题与方案

生成的 Xray `clients.email` 原为 `u7`、`u7.p3`，无法直接从访问日志识别用户名。
现改为 `eagle.u7`、`eagle.u7.p3`：前缀显示用户名，后缀继续以用户 ID 和档案 ID 归属流量，用户改名不会拆分数据库中的用量。

- `internal/domain/models.go`：生成可读标识，统计解析兼容新旧格式及包含点号的用户名。
- `internal/configdoc/compile.go`：默认档案和额外档案均传入用户名。
- `internal/app/runtime.go`：热暂停在新标识移除失败时尝试旧标识，兼容升级前已启动的 Xray；恢复用户时使用新格式。
- 无数据库迁移、依赖升级或凭据变更。

## 验证与独立评审

- `go test ./...` 通过。
- 补充默认档案、额外档案、用户名改名及分隔符、旧实例暂停恢复、热操作失败提示、新旧计数汇总的回归测试。
- 补充 VMess / Shadowsocks 文档生成与热添加标识一致性的集成用例，定向测试通过。
- 独立 agent review 完成，无需修复的明确问题。
- 在 `10.2.78.11` 使用独立临时 Xray 26.10.31 实例完成 VMess HTTP 请求，访问日志包含 `email: eagle.u7`，上下行计数使用相同新标识，热删除和热添加均成功；测试进程与临时文件已清理。

## 部署与回滚

更新管理服务后，重新应用受影响 Stack 的 Xray 配置并重启，对应日志才会改用新格式。尚未重启的旧实例仍可正常采集用量及暂停恢复。

旧版采集器无法解析新格式。若已经应用新配置，回滚时应先由新版补采流量，再恢复旧版生成配置并重启相关 Xray；不能仅替换管理服务 binary。用户及历史用量不需要迁移。
