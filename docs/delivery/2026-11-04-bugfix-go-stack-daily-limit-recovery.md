# Stack 每日阈值恢复修复

## 问题背景

Stack 达到每日流量阈值后会自动停止。跨自然日恢复时，旧实现调用全量 `Reconcile(true)`，可能把原本由管理员手动停止、但 `desired_running` 仍为 `true` 的 Stack 拉起。

## 根因分析

自动停止记录只保存 Stack、日期和触发时间，没有保存自动停止前各 unit 的实际运行状态。恢复逻辑只能依据配置中的期望运行状态，无法区分自动停止和管理员手动停止。

## 修复方案

- 为自动停止记录增加 `restore_xray` 和 `restore_mihomo` 字段。
- 触发自动停止前查询并保存 xray / mihomo 是否实际运行。
- 跨日恢复时按 mihomo → xray 顺序，只启动保存为运行状态且仍有生成物的组件，并检查启动后是否保持运行。
- 恢复失败时保留自动停止记录，下一轮继续重试；恢复期间手动停止组件会清除对应恢复位。
- 保留 `enabled` 和 `desired_running` 校验，配置上已停用的 Stack 不会恢复。

## 验证结果

- 新增回归测试：自动停止的运行组件跨日恢复。
- 新增回归测试：手动停止的 Stack 跨日不恢复。
- 新增回归测试：恢复顺序、恢复失败重试、恢复期间手动停止组件。
- `go test ./...` 通过。
- `go vet ./...` 通过。
- `git diff --check` 通过。

## 风险与后续建议

旧版本已经存在的自动停止记录，其新增恢复字段由迁移默认置为 0；升级后首次跨日不会自动拉起这些历史记录对应的组件，管理员可手动启动。
